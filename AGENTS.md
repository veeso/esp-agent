# AGENTS.md

Guidance for coding agents working in this repository.

## Project context

This repository is `esp-agent`, a `#![no_std]` library that aims to run a
local agent on ESP32 chips, with embeddable prompts, skills,
and context. It started as a fork of `qdrant-labs/static-models-bm`; keep the
credit to that project and its author in `README.md`. Today it runs static
embedding models on the Espressif chips with 16 MB of flash: the ESP32-S3
(default, Xtensa), the ESP32-S31 and ESP32-P4 (RISC-V,
`riscv32imafc-unknown-none-elf`), and the ESP32-C5 and ESP32-C6 (RISC-V,
`riscv32imac-unknown-none-elf`). `docs/src/boards.md` lists the supported chips
and why the others cannot hold the example model. The library ships no model: firmware embeds
its own with the `model!` macro. It is a virtual Cargo workspace: the library
lives in `crates/esp-agent` (`src/lib.rs`) and other ESP firmware projects
depend on it, `crates/esp-agent-macros` provides the build-time model compiler,
`crates/esp-agent-bench` holds unpublished criterion benchmarks that run on
regular computers, and `examples/semantic-search` is an example `#![no_main]` firmware generated by `esp-generate` for Espressif MCUs,
which embeds the potion-2M model.

Keep the library chip-agnostic: it must not depend on `esp-hal` or other chip
crates, enable chip features, or emit linker configuration. Chip setup, linker
scripts, and the heap belong to the firmware that uses the library.

The toolchain is the espup `esp` toolchain 1.97.0.0 with edition 2024. Keep
`rust-toolchain.toml`, the `version:` input of `esp-rs/xtensa-toolchain` in
`.github/workflows/ci.yml`, and `workspace.package.rust-version` in the root
`Cargo.toml` synchronized.

Shared package metadata (`version`, `edition`, `homepage`, `license`,
`repository`, and `rust-version`) lives in `[workspace.package]`, and every
member inherits it. Members declare only what is specific to them, such as
`name`, `description`, `categories`, and `keywords`.

The library also builds and tests on regular computers with the standard Rust
toolchain 1.97, through `just build_host` and `just test`. Keep `host_toolchain`
in `just/build.just` and `RUSTUP_TOOLCHAIN` of the `host` job in
`.github/workflows/ci.yml` and of the `benchmark` job in
`.github/workflows/benchmark.yml` equal to `workspace.package.rust-version`. Library code must
keep building for the host target as well as for every supported chip.

## Working rules

- Read the relevant source, documentation, configuration, and tests before
  making changes.
- Keep changes scoped to the requested task and preserve unrelated user work.
- Use existing project patterns before adding new abstractions.
- Add or update focused tests before changing behavior.
- Update user documentation when commands, public APIs, configuration, or
  workflows change.
- Always update the mdBook website in `docs/` when adding a new feature or
  changing the public API, in the same change that introduces it.
- Use `git`; never use `jj` or git worktrees.
- Never open a GitHub issue without prior user approval.
- Do not stage or commit local plans. Planning state belongs under the ignored
  `docs/superpowers/`, `.superpowers/`, or `.claude/plans/` directories.

## Source layout

- `crates/esp-agent/src/lib.rs` is the library root and defines the public
  `model!` macro.
- `crates/esp-agent-macros/` implements its `compile_model!` helper,
  which compiles a model folder at build time into a `RawModel` expression.
  The public `model!` macro passes it to the library constructor to build a `Model`.
- `crates/esp-agent/src/model.rs` is the `Model` value,
  `crates/esp-agent/src/tokenizer.rs` is the tokenizer,
  `crates/esp-agent/src/embedder.rs` is the embedder and its configuration,
  `crates/esp-agent/src/index.rs` is the vector index with payloads,
  `crates/esp-agent/src/knowledge.rs` is `Knowledge`, the store of texts agents borrow,
  `crates/esp-agent/src/agent.rs` is `Agent`, which answers prompts from a `Knowledge` store,
  `crates/esp-agent/src/retriever.rs` is the internal search the agent uses, and
  `crates/esp-agent/src/scratch.rs` is `Scratch`, the reusable buffers of the
  allocation-free paths.
- `crates/esp-agent-bench/` holds the host benchmarks: `src/lib.rs` has the shared
  model and inputs, `benches/` has one file per group (`tokenize`, `embed`,
  `search`), and `src/report.rs` renders the criterion results as Markdown for the
  `src/bin/bench_report.rs` binary.
- `crates/esp-agent/tests/fixtures/` holds the tiny model folders the integration tests embed.
- `examples/semantic-search/` contains two firmware binaries. The entry points
  are `src/main.rs` for `semantic-search` and `src/home_assistant.rs` for
  `home-assistant`. Both use `src/board.rs` for board initialization and
  `src/console.rs` for the sans-IO serial console. `model/` holds the
  potion-2M model downloaded by
  `just download_test_model` (it is not tracked), `build.rs` configures the
  linker, and `ld/<chip>/` holds the linker scripts of each RISC-V chip, copied
  from esp-hal with a 16 MB `ROM` region.
- Use `module_name.rs`; never introduce `mod.rs`.

- `docs/` contains the mdBook website. Pages in `docs/src/` include code from
  `examples/semantic-search/src/` through `ANCHOR` comments. Preserve these
  comments when editing the examples.

## ESP notes

- Build the example for exactly one chip per build: its `esp32s3` feature
  (default), or one of its `esp32s31`, `esp32c5`, `esp32c6`, and `esp32p4`
  features with `--no-default-features`. Never enable two. The library has no chip features.
- The S3 builds for `xtensa-esp32s3-none-elf`, the default target in
  `.cargo/config.toml`. The S31 and the P4 build for
  `riscv32imafc-unknown-none-elf`, the C5 and the C6 for
  `riscv32imac-unknown-none-elf`. Because targets are shared, `build.rs` picks
  the linker scripts from the chip feature.
- When adding a chip, add its example feature, `ld/<chip>/` scripts, the UART0
  receive pin in `src/board.rs`, its `just` recipes, the CI `quality` matrix
  entry, and its rows in `README.md` and `docs/src/boards.md`.
- Check the `generator parameters:` comments in `examples/semantic-search/src/main.rs` before
  changing code that depends on selected generation options.
- Avoid `std`; use `core` and embedded-friendly crates.
- `alloc` is enabled. If allocations fail, adjust the
  `esp_alloc::heap_allocator!` size for the target chip in
  `examples/semantic-search/src/board.rs`.
- `.cargo/config.toml` contains the generated target, runner, build flags, and
  `[env]` defaults. Espressif crates expose additional configuration through
  environment variables; use `esp-config` to inspect and set those options. The
  linked "Additional configuration" sections for the enabled Espressif crates
  document crate-specific variables; keep project-specific defaults in `[env]`
  instead of hard-coding them in source.
- Logging uses `log` and `esp-println`; the default filter is `ESP_LOG=info` in
  `.cargo/config.toml` and can be overridden from the environment.
- `just run_s3` and `just run_s31` flash the board and open the monitor through
  the `espflash` runner in `.cargo/config.toml`. `just run_c5`, `just run_c6`,
  and `just run_p4` pass their runner with `--config`, because they share a
  target with another chip. The S31 runner uses
  `--flash-size 16mb`.
- If flashing fails, check bootloader mode, serial-port permissions, the
  selected port when multiple boards are connected, and that the `--chip` in
  `.cargo/config.toml` matches the target.

## Rust conventions

- Follow `rustfmt.toml` and format Rust through `just fmt`.
- Clippy must pass with warnings denied.
- Public library modules and items require canonical rustdoc documentation.
  Doctests cannot run on the device, so examples are not required.
- Avoid `unsafe` unless the task requires it and its safety invariants are
  documented.
- Use named format placeholders instead of positional `{}` arguments.
- Prefer `#[expect]` with a reason over `#[allow]` for local lint overrides.
- Keep dependency entries and feature definitions alphabetically sorted.
- Use bare, minimal dependency versions in `Cargo.toml`.

## Command interface

Use [`just`](https://just.systems) recipes when one exists. Do not bypass a
recipe with an ad hoc `cargo` or tool command. If a recurring task has no
recipe, add a focused recipe before using it.

Run `just` to list every command. Recipes with the suffix `_s3`, `_s31`, `_c5`,
`_c6`, or `_p4` run for one chip. For recipes with chip variants, the
unsuffixed recipe runs every chip: `_s3`, `_s31`, `_c5`, `_c6`, and then `_p4`. The primary recipes are:

```sh
just build
just build_s3
just build_s31
just build_c5
just build_c6
just build_p4
just build_host
just download_test_model
just run_s3
just run_s31
just run_c5
just run_c6
just run_p4
just monitor
just lock
just fmt
just fmt_check
just clippy "-- -D warnings"
just doc
just book
just book_serve
just test
just coverage
just test_bench
just bench_all
just bench <group>
just bench_smoke
just bench_report
just clippy_bench "-- -D warnings"
just deny
just scan_secrets
just check
just setup_githooks
```

`just check` is the required local quality gate. It checks formatting, then runs
Clippy and rustdoc with warnings denied for each chip. It builds the library for
the host with `just build_host`, lints the benchmarks with `just clippy_bench`,
runs the host library tests once with `just test`, tests the benchmark report
with `just test_bench`, and checks the workspace dependency policy once with
`just deny`. The benchmark crate needs `std`, so the chip Clippy recipes exclude it.

When invoking compilation commands from the CLI, never request parallelism
greater than eight. This is an invocation constraint; do not encode the local
cap in tracked project files.

## Required tools

The local recipes expect:

- espup with the `esp` toolchain 1.97.0.0, and rustup.
- The standard Rust toolchain 1.97 (`rustup toolchain install 1.97`).
- espflash 4.6.0 or newer.
- just.
- mdBook 0.5.4 and mdbook-mermaid 0.17.1 (`cargo install mdbook-mermaid
  --version 0.17.1 --locked`). `docs/mermaid.min.js` and `docs/mermaid-init.js`
  are generated by `mdbook-mermaid install docs`; do not edit them.
- dprint 0.56.1 and nightly rustfmt.
- cargo-deny.
- cargo-llvm-cov and the `llvm-tools-preview` component of Rust 1.97.
- TruffleHog.
- git-cliff.
- zizmor for workflow changes.
- shellcheck for shell hook changes.

If a required tool is unavailable, report it explicitly. Do not claim its check
passed or silently replace the repository command with a weaker check.

## Documentation

- Update the pages in `docs/src/` whenever you add a new feature or change the
  public API or the firmware examples. Add a new page, and list it in
  `docs/src/SUMMARY.md`, when a feature has no page yet.
- Run `just book` after editing `docs/` to confirm the website still builds.
- Write task-oriented documentation with runnable examples.
- Use ATX headings and fenced code blocks with language identifiers.
- Keep Markdown lines readable, tables aligned, and files terminated by one
  newline.
- Run `fmt-md-tables -i <file>` after editing a Markdown file that contains a
  table.

## GitHub Actions

- Run `zizmor .github/workflows` after every workflow change until it exits
  successfully with no findings.
- Pin every external action to the full commit SHA of its latest stable release
  and record the exact matching tag in a trailing comment.
- Declare explicit least-privilege permissions.
- Set `persist-credentials: false` on checkout steps unless later authenticated
  Git operations are explicitly required.
- Never interpolate attacker-controlled GitHub expressions directly into a
  shell script. Pass values through `env` and quote the shell variable.

## Git and releases

- Name issue branches `{conventional-commit-action}/{issue_number}-{slugified-issue-title}`.
  Use the Conventional Commit type for the work, the issue number without
  `#`, and a lowercase, hyphen-separated title, as in `feat/26-declarative-turns`.
- Use Conventional Commits with an imperative, lower-case description.
- Do not add agent attribution, session links, or agent `Co-Authored-By` lines.
- Inspect the diff before staging or committing changes.
- Generate release notes with `just changelog_preview <version>` and
  `just changelog <version>`.
